# Preventing Sleep on a Fedora VM

## Overview

On a Fedora guest under VMware Fusion, "going to sleep" can come from as many as three independent layers, and the CLI fix only works if it targets the layer that's actually firing:

1. **systemd-logind's idle action** — suspends the machine after all seated sessions report idle, controlled by `IdleAction` / `IdleActionSec` in `logind.conf`. This mainly watches local console/graphical sessions; a plain SSH session usually doesn't count toward it.
2. **GNOME's power daemon** (only if a desktop session is running) — `gnome-settings-daemon` keeps its own idle timer and calls suspend directly, independent of logind's `IdleAction`.
3. **The macOS host itself sleeping** — this pauses the whole VM no matter what the guest is configured to do. It isn't a guest-CLI setting, so it's covered briefly at the end rather than being the main focus.

This guide's approach: first raise the baseline idle timeout to an hour or more at whichever of the first two layers applies to this VM, then add a tag-based watcher on top that grabs a `systemd-inhibit` sleep lock whenever a named process is running. That lock is honored by both logind and GNOME's power daemon, so it overrides either one without needing to know in advance which layer would have triggered sleep.

## Baseline idle timeout: systemd-logind

This is the layer that matters for a headless or console session, and it's the one to set even if a desktop is also in use. Use a drop-in file rather than editing `/etc/systemd/logind.conf` directly, so the setting survives package updates:

```bash
sudo mkdir -p /etc/systemd/logind.conf.d
sudo tee /etc/systemd/logind.conf.d/99-idle-timeout.conf <<'EOF'
[Login]
IdleAction=suspend
IdleActionSec=1h
EOF
sudo systemctl restart systemd-logind
```

- `IdleActionSec=1h` is systemd's time syntax — it accepts `1h`, `90min`, `3600`, etc. Raise it further (`2h`, `4h`) if an hour isn't enough.
- `IdleAction` can also be `ignore` (never act on idle at all, leaving that decision entirely to GNOME or to nothing), `poweroff`, `hibernate`, or `suspend-then-hibernate`. `suspend` matches "go to sleep."
- Restarting `systemd-logind` is normally safe and picks up the new config immediately; if a running console session behaves oddly afterward, a reboot applies it just as well.
- This idle action only fires for a *seated* session that logind tracks as idle (keyboard/mouse or a local console) — a session reached purely over SSH typically never registers as idle, so on a headless VM this setting may end up doing nothing at all. If sleep is still happening on a headless box, it's coming from somewhere else (a cron job, `systemctl suspend` in a script, or the host) — check the troubleshooting section below.

## Baseline idle timeout: GNOME desktop

Skip this section on a headless/minimal Fedora VM. If this VM runs Fedora Workstation with GNOME (i.e. VMware Fusion is showing a full desktop), `gnome-settings-daemon` calls suspend on its own timer, separate from logind's `IdleAction`, so it needs its own setting:

```bash
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-timeout 3600
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-type 'suspend'
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-battery-timeout 3600
gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-battery-type 'suspend'
gsettings set org.gnome.desktop.session idle-delay 3600
```

- The `*-timeout` keys are seconds (3600 = 1 hour); the `*-type` keys are `suspend`, `hibernate`, or `nothing` (set to `nothing` to disable automatic suspend from this layer entirely and rely only on logind or the tag-based watcher below).
- `idle-delay` controls screen blanking/lock, not suspend itself — harmless to leave alone, but setting it to match avoids the screen locking long before the machine actually sleeps.
- `gsettings` talks to the GNOME session's own D-Bus, so it has to run *inside* that session. A terminal opened on the VM's own desktop already has the right environment. Running it remotely over SSH instead requires pointing at that session's bus explicitly:

```bash
GNOME_UID=$(id -u your_username)
sudo -u your_username DBUS_SESSION_BUS_ADDRESS="unix:path=/run/user/${GNOME_UID}/bus" \
  gsettings set org.gnome.settings-daemon.plugins.power sleep-inactive-ac-timeout 3600
```

## Tag processes that must block sleep entirely

`systemd-inhibit` takes a lock that both `systemd-logind` and GNOME's power daemon check before suspending. Two lock types matter here: `sleep` (blocks suspend/hibernate outright) and `idle` (blocks the idle timer that would otherwise lead to it). For a command launched directly, wrapping it is enough on its own:

```bash
systemd-inhibit --what=sleep:idle --why="Running backup" --mode=block rsync -a /src /dst
```

That only helps for jobs started through the wrapper, though. To block sleep whenever a *named* process happens to be running — however it was started — a small watcher polls for it and takes the lock on its behalf.

**The watcher script** — `/usr/local/bin/idle-guard.sh`. Edit `WATCHED_PROCS` to tag whatever should block sleep:

```bash
#!/usr/bin/env bash
# Edit this list to "tag" the processes that should block sleep while running.
WATCHED_PROCS=(
  "rsync"
  "borg"
  "my-backup-job.sh"
)

CHECK_INTERVAL=30   # seconds between checks
LOCK_DURATION=45    # must exceed CHECK_INTERVAL so locks overlap with no gap

pattern=$(IFS='|'; echo "${WATCHED_PROCS[*]}")

while true; do
  if pgrep -f -- "$pattern" > /dev/null 2>&1; then
    systemd-inhibit \
      --what=sleep:idle \
      --who="idle-guard" \
      --why="Tagged process running" \
      --mode=block \
      sleep "$LOCK_DURATION" &
  fi
  sleep "$CHECK_INTERVAL"
done
```

Every 30 seconds it checks whether any tagged name matches a running process's full command line (`pgrep -f`). A match spawns a background `systemd-inhibit … sleep 45 &` that holds the lock for 45 seconds — longer than the 30-second check interval — so a fresh overlapping lock is always taken before the previous one expires, giving continuous coverage with no PID bookkeeping or explicit release. Once no tagged process is present, no new lock gets started and the last one simply lapses within under a minute.

**Run it as a service** so it survives reboots and restarts itself if it ever dies:

```bash
sudo chmod +x /usr/local/bin/idle-guard.sh

sudo tee /etc/systemd/system/idle-guard.service <<'EOF'
[Unit]
Description=Block sleep while tagged processes are running

[Service]
ExecStart=/usr/local/bin/idle-guard.sh
Restart=always
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

sudo systemctl daemon-reload
sudo systemctl enable --now idle-guard.service
```

To change which processes are tagged later: edit the `WATCHED_PROCS` array in the script, then `sudo systemctl restart idle-guard.service` — no rebuild needed.

**A naming caveat:** `pgrep -f` matches against the *entire* command line, so a short, generic tag (`sync`) can match unrelated processes that merely mention that word in an argument or path. Prefer distinctive names, or use `pgrep -f -x` for an exact full-command-line match, or plain `pgrep -x` for an exact match against the process's short name (note the kernel truncates that name to 15 characters).

## Verify and troubleshoot

| Command | What it shows |
| --- | --- |
| `systemd-inhibit --list` | Every active lock, who holds it, and why — while a tagged process runs, `idle-guard` should appear here holding `sleep`/`idle`. |
| `journalctl -u idle-guard.service -f` | The watcher service's own status and restarts. |
| `loginctl session-status $(loginctl --no-legend list-sessions \| awk '{print $1}' \| head -1)` | `IdleHint` / `IdleSinceHint` for the current session — confirms whether logind's idle timer is advancing at all. |
| `cat /etc/systemd/logind.conf.d/99-idle-timeout.conf` | Confirms the drop-in is in place with the intended values. |
| `gsettings get org.gnome.settings-daemon.plugins.power sleep-inactive-ac-timeout` | Confirms GNOME's own timeout, if a desktop session applies. |

Common pitfalls:

- **Sleep still happens almost immediately.** Something else is likely calling suspend directly — check `systemctl list-timers`, `crontab -l`, and any script that runs `systemctl suspend` on its own schedule.
- **The tagged process runs but sleep still happens.** Confirm the pattern actually matches: run `pgrep -f -- "the-pattern"` by hand while the process is active, and double-check the real command line with `ps -ef | grep <name>`.
- **On a headless VM, `IdleActionSec` never seems to fire at all.** That's expected — without a seated session, logind's idle tracking has nothing to measure. The watcher service and any deliberate `systemctl suspend` are the only things actually controlling sleep in that case.

## Host-side note (if the whole VM freezes, not just the guest)

VMware Fusion has no idle-sleep timer of its own for a VM. A running VM keeps running until either the guest OS suspends itself (everything above) or the macOS host sleeps, which pauses the entire VM regardless of any guest setting. If the VM still appears to freeze after inactivity with all of the above in place, the host is the more likely cause.

From macOS, `caffeinate` is the host-side equivalent of the inhibitor lock used above — it can be tied to VMware Fusion's own lifetime:

```bash
# Run on the macOS host, not inside the Fedora guest:
caffeinate -i -w $(pgrep -x "VMware Fusion")
```

`-i` blocks idle sleep, `-w <pid>` ties the lock to that process and releases automatically when it exits. `pmset -g assertions` lists active power assertions if it's ever unclear what's currently holding the Mac awake.
