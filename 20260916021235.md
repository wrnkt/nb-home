## Notes

We need to make good use of feature flags so we can streamline as more people use the project.

> [!NOTE]
> Make sure we support lists of args, dirs & files: 
> e.g, `dtfls add ~/.bashrc ~/.profile ~/.config/shell/`
> this may need to apply for other commands as well

> [!IMPORTANT]
> Backing this system with `git` version control allows leveraging the `git` API for reverting mistakes, 
> reconciling the same config file in different branches, etc.


When a user calls `dtfls add ~/.bashrc`, they are expecting that file to be considered "tracked", meaning it has an entry in the `track` key of the configuration file. When running `dtfls adopt` afterwards, they'd expect the current state of their `~/.bashrc` be copied into `dtfls` tracking repo.

Perhaps it's best that we ask a y/n for each file being "adopted" along with a diff (dtfls tracked vs. system version).
This could easily snowball out of control & make the user's experience uncomfortable. Hide that possible confirmation workflow behind a feature flag.
